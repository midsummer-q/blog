HTTP 能表达“请给我这篇文章”，却不单独解决沿途有人偷看、修改或冒充网站的问题。HTTPS 在 HTTP 通信外加入安全机制，让浏览器可以验证对方，并保护传输内容。

本篇不从密码学公式开始。先分清“加密”“身份验证”和“完整性”三件事，再解释证书与密钥各做什么，最后看一次常见的 TLS 1.3 握手。

## Table of contents

## 网络上的三个问题，不是一个锁就能概括

假设你在网站提交信息，沿途观察者可能尝试做三件事：阅读内容、修改内容、冒充接收者。它们对应三种保护目标。

**机密性**：无权获得密钥的人，不能轻易从截获内容恢复原文。**完整性**：受保护消息被改动后，接收方能够发现。**身份认证**：浏览器有依据确认正在通信的一端有权代表你访问的域名。

如果只加密，却把密钥与冒充者协商好，冒充者一样能读明文。如果只验证了一个名称，却明文传送后续内容，沿途仍可能被看见。所以需要把这些机制组合起来。

**TLS** 是用于建立这种安全通信的协议。HTTPS 就是 HTTP 通过这种安全机制传输的常见使用方式。早期技术名叫 SSL，日常仍有人说“SSL 证书”，但不要把这个习惯叫法等同于应启用老旧 SSL 协议。

## 明文、密文、密钥，分别是什么？

**明文** 是通信双方实际要处理的原始内容，例如一条 HTTP 请求。**密文** 是加密后的数据。**密钥** 是加密算法使用的秘密参数；没有合适的密钥，不能把密文当普通文字直接阅读。

可以把加密比作给内容上锁，但现实中密钥不是一串“可以凭感觉猜”的口令，现代算法也不是简单把每个字母换成下一个字母。教学类比只用来区分内容与开锁依据，不能当成真实算法。

**对称加密** 使用双方共享的秘密来保护数据，适合传输大量内容。**公钥与私钥** 则是一对相关的参数：公钥可以公开，私钥必须由持有者保护。它们在数字签名、身份认证等机制中发挥作用。

不同算法的用途不能随意互换。尤其不要把现代 TLS 1.3 背成“所有正文都直接用证书公钥加密”；实际通信会派生专门的流量密钥。

## 证书不是网站密码，而是经过签名的信息

设浏览器访问 `www.example.com`。网站给出一份证书，其中包含名称、公钥、有效期等信息。签发者用数字签名把这些信息联系起来，客户端按信任配置验证。

**数字签名** 可以先理解为：持有私钥的一方对数据产生可验证的证明，其他人用对应公钥验证它。它不是把手写签名扫描进去，也不是把证书内容藏起来。

**CA** 是证书颁发机构。浏览器或操作系统维护一组信任锚，通常体现为受信任根证书。服务器提供的证书可能由中间 CA 签发，中间 CA 再连到受信任根，这条验证关系称为 **证书链**。

关键点是“本地原本信任谁”。服务器随便发来一张写着“我是根”的证书，并不能让浏览器自动相信它。否则任何冒充者都能自己签发自己的身份证明。

## 浏览器至少要把几个问题分开检查

1. 这张证书能否按规则连接到本地信任的签发关系？
2. 证书覆盖的名称，是否匹配我正在访问的域名？
3. 当前时间是否处在证书有效期内？用途及其他适用约束是否满足？
4. 对方是否能在本次握手中证明拥有相关私钥，而不只是复制了一份公开证书？

例如，某张证书即使可信地签发给 `shop.example`，也不能拿来证明 `bank.example`。同样，系统时间错误可能导致有效期检查失败。浏览器的证书警告在提示具体检查没有满足，不能靠“网页看起来正常”替代验证。

HTTPS 认证的是域名相关的通信身份，不是商家的诚信。一个诈骗网站也可以为自己拥有的域名取得有效证书，因此仍需要判断你输入的名称是否正确。

## 不在网上发送最终秘密，怎样一起算出秘密？

常见 TLS 1.3 完整握手使用临时密钥交换。双方各自产生私密部分，交换可公开的密钥份额，再分别计算出一致的共享秘密；协议继续从中派生不同阶段使用的密钥。

这里不要求你先会椭圆曲线数学，只需知道两点：网上交换的公开份额不等于最终流量密钥；身份认证还要与这次交换绑定，否则旁观者可能分别冒充两端。

证书的长期认证密钥与本次连接的临时交换材料也不是同一个东西。将它们分开，才能理解后文为什么会提到“前向保密”，而不是把所有秘密统称为一个密码。

## 读握手图时，按动作分四组

第一组是打招呼与协商：“我支持哪些方式，这里是我的公开份额。”第二组是共同形成握手阶段的密钥。第三组是证明身份并检查这段握手没有被改变。第四组才是用应用流量密钥保护 HTTP 数据。

图中的 `ClientHello` 是客户端打招呼的消息，`ServerHello` 是服务器选择参数的回应；`Certificate` 是证书消息；`Finished` 则用于确认握手记录与密钥推导的一致性。第一次看图不必记英文全拼，先按这四组动作读。

下面的具体流程选择常见的服务器证书认证、TLS 1.3 完整握手。恢复连接和其他模式会不同，先学这一条主线即可。

## HTTPS 在保护哪一段？

对于直接连接，TLS 建立在客户端与服务器之间，HTTP 内容在这段连接中受到保护。若网站前面有终止 TLS 的反向代理，浏览器实际与代理握手，代理再通过另一段连接访问源站。

因此，“浏览器地址栏是 HTTPS”不自动证明代理到源站也加密。要画清每一段连接由谁终止、谁持有密钥、谁能读取明文，再讨论保护范围。

| 目标           | TLS 提供的机制方向         | 不代表什么                    |
| :------------- | :------------------------- | :---------------------------- |
| 保密           | 用协商出的流量密钥加密记录 | 隐藏所有网络元数据            |
| 完整性         | 检测受保护内容被篡改       | 保证应用逻辑正确              |
| 服务器身份     | 证书验证与握手认证         | 网站内容值得信任、没有诈骗    |
| 可选客户端身份 | 客户端证书等机制           | 普通 HTTPS 默认就完成用户登录 |

终端中毒、服务器被入侵或应用主动泄露内容，都不在“网络传输加密”能够独自解决的范围内。

## 证书里有什么，又没有什么？

证书把公钥与名称等信息绑定，由签发者签名。客户端会根据本地信任配置，尝试构建并验证到受信任根的路径，同时检查目标名称、有效期、用途及其他适用约束。

服务器通常发送叶子证书和必要的中间证书；受信任根一般来自客户端的信任库，不需要因为服务器把某张根证书附上，就接受它为可信。

**证书包含公钥，不包含服务器的私钥。** 任何人可以复制公开证书，但没有对应私钥，不能正常完成需要该私钥的握手签名。证书不是一段需要保密的“网站密码”。

名称也必须匹配。浏览器访问 `www.example.com`，不能因为某个服务器有一张受信任 CA 签发给 `other.example` 的证书，就认定它是目标。证书路径可信与名称正确是两项不同检查。

主机时钟明显错误时，有效期判断也会出问题。排查证书失败，应核对具体错误、目标名称、证书链和系统时间，而不是一律关闭验证。

## 不提前共享秘密，怎样得到共享密钥？

常见 TLS 1.3 完整握手使用临时 Diffie-Hellman 类密钥交换，例如椭圆曲线变体。双方交换公开参数，各自保留私密部分，随后推导出共享秘密，再结合握手上下文派生不同用途的密钥。

这个描述中的“公开参数”可以在网络上发送。安全性依赖于：仅凭公开信息，攻击者难以计算相应共享秘密。它不是“客户端生成会话密钥，再永远用证书公钥加密发给服务器”的通用流程。

临时密钥交换还支持前向保密目标：在相应秘密妥善销毁、算法和实现满足要求的前提下，未来长期认证私钥泄露，不应直接解密过去捕获的会话。这并不保护已经被记录下来的端点明文。

[密钥交换与认证的具体组合由 TLS 1.3 规范定义](https://www.rfc-editor.org/rfc/rfc8446.html)。PSK、恢复会话和不同模式存在差异，本文图示只取一种常见情况。

## TLS 1.3 的一次常见完整握手

![TLS 1.3 常见证书握手：公开 hello 和密钥份额，随后加密的认证消息、Finished 与应用数据。](../../assets/images/network-basics/12-tls-trust.svg)

1. 客户端发送 ClientHello，表达支持的版本、算法、密钥份额和其他扩展。
2. 服务器选择参数并返回 ServerHello，双方据此建立握手阶段的密钥。
3. 服务器发送受保护的扩展、证书、CertificateVerify 和 Finished 等消息。
4. 客户端验证证书及握手认证，发送自己的 Finished，随后使用应用流量密钥通信。

这里的 CertificateVerify 用于把认证私钥与当前握手上下文关联起来；Finished 用于验证握手记录及密钥推导的一致性。不能把它们都简称为“证书校验”，否则容易忽略握手本身也需要防篡改。

TLS 1.3 在 ServerHello 之后保护大部分握手消息，因此被动抓包通常不能像旧式未加密示意图那样直接读到服务器证书。浏览器的证书查看器与抓包文件展示的是不同观察渠道。

## 进阶：SNI、ALPN 与证书各管一件事

同一个入口可能承载多个域名。SNI 帮助服务器在握手时选择相应站点配置；ALPN 用于协商应用协议，例如 HTTP/2 或 HTTP/1.1；证书验证则确认对端是否被授权代表目标名称。

发送了 SNI，不等于已经验证证书。协商到 `h2`，也不表示网站业务正常。

在没有适用加密 ClientHello 机制的情况下，握手中的一些信息仍可能对路径观察者可见；即使隐藏了部分名称，目的 IP、时序与流量大小也仍会暴露信息。HTTPS 不能简单等同于“别人完全不知道我在连谁”。

## 进阶：恢复与 0-RTT 为什么需要额外小心？

后续连接可以利用先前建立的状态减少握手开销。某些 TLS 1.3 恢复场景还允许客户端更早发送 0-RTT 数据。

更早发送不意味着比完整握手拥有更多安全保证。早期数据存在重放风险，服务端必须结合应用语义与防重放策略决定是否接受；不能把扣款之类不可随意重复的操作当作普通静态资源处理。

也不要把“使用 TLS 1.3”说成“每一次都是 0-RTT”。完整握手、恢复、是否允许早期数据，以及底层传输本身，都影响真实时延。

## 不写代码的观察：查看浏览器验证的是谁

打开一个 HTTPS 网站，点击地址栏旁的网站信息按钮。不同浏览器可能显示锁形、设置形或其他图标，不要以图标样式判断协议版本。进入连接安全信息，找到证书查看入口；也可在开发者工具的安全信息区域查看。

依次找三项：证书覆盖的域名、有效期、签发者。再把覆盖的名称与地址栏里的域名对照。证书名称可能使用符合规则的通配形式，因此不一定与完整主机名逐字相同。

这是通过浏览器查看其连接的证书信息，不是在网络上被动抓包。TLS 1.3 的部分握手内容本身已经加密，两种观察渠道能看到的内容并不相同。

## 可选编程实验：检查本地 TLS 客户端的验证默认值

保存为 `tls_defaults.py`，按[Python 准备说明](/blog/posts/understanding-ports-and-sockets/#可选编程实验的准备怎样运行本系列的-python-代码)运行。`ssl` 是 Python 的安全通信模块，`context` 是保存验证规则等配置的对象；两个打印项只检查规则是否开启，不进行真实网站访问。

后面的 OpenSSL 命令属于进一步观察。如果没有安装这个独立工具，可以跳过，不影响前面的浏览器练习。

下面代码不联网，只检查 Python 创建的客户端默认上下文：

```python
import ssl

context = ssl.create_default_context()
print("certificate required:", context.verify_mode == ssl.CERT_REQUIRED)
print("hostname checking:", context.check_hostname)
```

正常应输出两个 `True`。这说明默认上下文要求验证证书并检查主机名，**不证明任何具体站点的证书已经验证通过**。真正握手还需要加载可用信任库、连接目标，并提供正确的服务器名称。

如果本机装有 OpenSSL，可以由你在自己的网络环境中执行：

```bash
openssl s_client -connect example.com:443 -servername example.com -verify_hostname example.com -verify_return_error
```

这里显式指定 SNI、验证名称和遇到验证错误就返回失败。观察协商版本、证书链与验证结果；示例没有预设具体证书颁发机构或到期日，因为这些会变化。命令在握手后可能继续等待输入，可用 Ctrl+C 结束。

[OpenSSL s_client 文档](https://docs.openssl.org/3.5/man1/openssl-s_client/)解释了这些选项。它使用的信任配置可能与浏览器不同，因此命令成功或失败都应结合具体环境解释。不要只从“工具打印了证书”推出验证已成功。

## 把浏览器报错翻译成下一步行动

- 名称不匹配：核对访问的域名、SNI、证书覆盖范围和代理配置。
- 证书过期或尚未生效：核对证书时间以及本机时钟。
- 找不到可信签发链：检查中间证书是否齐全、客户端信任库是否适用。
- 握手成功但请求失败：继续进入 HTTP 状态、权限和应用日志。

关闭证书验证只会移除一项关键检查，不会把错误名称或不可信链变成正确配置。开发环境确有自签名需求时，也应明确配置自己的信任根与名称，而不是把忽略错误带入生产客户端。
